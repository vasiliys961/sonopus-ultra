# Doctor Opus Ultrasound (Sono) — окончательное ТЗ
### Версия 2.0 FINAL · Для Cursor / Grok 4.7 / GPT-5.3-Codex · Объединяет все обсуждения, включая внешний анализ, в один документ

---

## 1. Цель и границы проекта

**Doctor Opus Sono — самодостаточный, значительно более мощный аналог диагностического модуля Doctor Opus, специализированный на УЗИ.** Не тонкий поставщик данных, а полноценный продукт, который сам:

1. подключается к УЗИ-аппарату (хендхелд/портативный/стационарный, любой производитель) через один из доступных открытых каналов;
2. в реальном времени помогает врачу навести датчик на стандартную проекцию (эвристический Quality Gate, без ML в v1);
3. по достижении диагностического качества фиксирует клип, извлекает структурированные наблюдения через LLM (Gemini 3.8 — Brain 1) и **сам ставит предварительный дифференциальный диагноз** через вторую, более мощную модель (Sonnet/GPT — Brain 2) с промптом опытного врача УЗИ-диагностики;
4. проводит результат через диагностический арбитр (проверка evidence-привязки, отсутствие необоснованных гипотез) и показывает врачу для подтверждения/правки.

**Doctor Opus не является обязательным звеном.** Вся диагностическая функция Sono работает самостоятельно, без него. Если Sono установлен в клинике, где уже используется Doctor Opus, **уже подтверждённый врачом** результат может быть опционально передан туда (§5) для сопоставления с анамнезом и другими исследованиями пациента — но это дополнительная возможность, не часть основного цикла.

**Sono — не форк кода Doctor Opus.** Он переносит и адаптирует конкретные архитектурные наработки (§3.1) — паттерн реестра адаптеров, пайплайн анонимизации, абстракцию над LLM-провайдером — но является отдельным продуктом с собственным циклом релизов.

**Явно НЕ входит в цель проекта:**
- заменить врача или выдать диагноз без его подтверждения как финальный;
- полная поддержка допплера, эластографии и прочих продвинутых режимов в MVP.

(Полный список отложенного — §11, с дорожной картой возврата каждого пункта в разработку — §11.1.)

## 1.1 Продуктовая перспектива — честная оценка

**Ниша реальна и не переполнена.** Мировые лидеры (GE Caption AI, Exo, UltraSight, Butterfly) все привязаны к **своему** железу — это стратегия "продай аппарат, ИИ — бонус внутри". Слой, который делает **чужие**, уже купленные врачом дешёвые датчики "умнее" без покупки нового аппарата за $8-15 тыс., — реже встречающаяся позиция, особенно на рынках (включая РФ/СНГ), где доступ к премиальным западным AI-enabled системам ограничен санкционно или ценой, а дешёвые китайские зонды уже массово куплены и лежат "как есть", без всякого guidance.

**Честный минус против конкурентов**: у Caption AI подсказка встроена прямо в интерфейс аппарата — бесшовно. У Sono это "надстройка снаружи" через граббер — на старте это менее элегантно (лишний кабель/переходник), но зато не требует смены железа и работает с уже купленным датчиком любого возраста и бренда — позиционирование "сделай свой $300-500 зонд похожим по возможностям на $8000+ AI-enabled" честнее и убедительнее, чем попытка конкурировать в изяществе интеграции.

**Реалистичная последовательность выхода на пользу**: даже без единого ML-классификатора и без клинической валидации (см. §12 п.3) MVP уже даёт две проверяемые вещи — эвристический quality-контроль кадра (полезно само по себе для неопытного оператора) и структурированное второе мнение по уже готовому изображению. Обе ценности не требуют "дождаться идеальной ML-модели", чтобы быть полезными хоть кому-то уже на Фазе 1.

**Главный риск — не технический, а операционный**: рынок хендхелдов ежегодно обновляет модели/приложения/UI, у каждого свои мелкие особенности зеркалирования экрана — постоянное сопровождение совместимости, а не разовая разработка, стоит закладывать в ресурс так же, как поддержку браузерных версий.

## 2. Пользовательские сценарии

### 2.1 Guided Mode («для чайника» — врач общей практики / неопытный оператор, хендхелд)
- Устройство: портативный УЗИ-аппарат (западный или китайский), подключаемый к смартфону/планшету/ноутбуку.
- Поведение: врач просто водит датчиком над областью исследования → приложение само захватывает подходящие кадры → живые эвристические подсказки по ходу → автозахват при достижении качества → Brain 1 извлекает наблюдения → Brain 2 формирует гипотезы.
- **Ключевое отличие от Second Opinion Mode**: рассчитан на то, что качество съёмки будет не идеальным (неопытная рука, артефакты, не все стандартные виды получены). Система обязана явно учитывать это через `outcome: 'low_confidence_hypothesis'` (§6.4) — не отказываться от ответа при несовершенных данных, а честно давать предположительные гипотезы как один из диагностических опорных пунктов, с явным перечислением, что именно ограничивает достоверность.
- Первые протоколы (см. §6.3): мочевой пузырь, IVC.

### 2.2 Second Opinion Mode (подготовленный врач, стационарный аппарат)
- Устройство: стационарный УЗИ-аппарат, работающий полноценно; врач сам ведёт исследование.
- Приоритет: не пропустить находку, ускорить оформление протокола, дать второе мнение.
- Поведение: фоновое наблюдение за экраном (HDMI/screen capture) в реальном времени, минимум guidance, акцент на извлечение сущностей (в т.ч. распознавание уже нанесённых на кадр измерений/каллиперов аппарата) и клиническую трактовку.

Оба сценария используют один и тот же технический ствол (§3); различие — в UI-режиме и в весе Quality Gate/Guidance относительно Vision Engine.

## 3.1 Стратегия репозитория: перенос наработок Doctor Opus + чем обогатить сверх простого переноса

**Репозиторий: новый, отдельный** (`doctor-opus-ultrasound` или аналогичное имя) — не форк и не подпапка внутри Doctor Opus, независимый цикл релизов (CV/ML-часть меняется быстрее, чем стабильное клиническое ядро). Связь с Doctor Opus — только через контракт данных (§5), не через общий код по умолчанию.

**Что переносится (адаптируется, не копируется вслепую) — конкретные файлы Doctor Opus, уже проверенные в коде:**

| Откуда (Doctor Opus) | Что берём | Как адаптируется в Sono |
|---|---|---|
| `lib/device-hub/types.ts`, `factory.ts`, `device-hub.ts` | Паттерн `IDeviceAdapter`/реестра адаптеров | Тот же контракт, расширенный `stream-video` (§6.1) |
| `components/CameraCapture.tsx` | Базовая логика `getUserMedia`/`enumerateDevices`, выбор устройства | Отправная точка для `uvc-hdmi-adapter`, превращается из разового снимка в непрерывный поток |
| `lib/video-frame-extractor.ts` | Адаптивное извлечение кадров + анонимизация | Переиспользуется для Study Mode (DICOM-клипы), логика анонимизации — без изменений |
| `lib/video.ts` (+ `lib/prompts.ts`) | Двухэтапный Gemini-пайплайн (`getDescriptionPrompt`/`getDirectivePrompt`) | Brain 1 в §6.4 — та же схема вызова, новый набор промтов под структурированный JSON вместо свободного текста |
| `lib/llm-provider.ts` | Абстракция над провайдером модели (OpenRouter-совместимый) | Переносится как есть — Sono не должен быть жёстко привязан к одному провайдеру |
| `lib/ultrasound-reference-links.ts` | Ссылки на POCUS Atlas/Radiopaedia по находкам | Переиспользуется в Guided Mode для визуального сравнения "на что похоже" прямо во время сканирования |

**Чем обогатить сверх простого переноса:**

1. **Voice-to-Protocol в реальном времени.** У Doctor Opus уже есть запись разговора врач-пациент и STT (Polza/Aiesa/Whisper) → docx. У врача с УЗИ руки заняты датчиком — голосовой ввод здесь не удобство, а единственный практичный способ добавить комментарий без остановки сканирования. Приоритетная, не косметическая фича.
2. **Живое визуальное сравнение с атласом.** Doctor Opus уже индексирует личную библиотеку изображений для visual search. В Guided Mode — "похожие находки из атласа" рядом с live-картинкой.
3. **Непрерывность с картой пациента.** Если Sono используется в той же клинике, что и Doctor Opus, — исследование сразу привязывается к уже существующей карте пациента.
4. **PWA/офлайн-режим.** Doctor Opus уже собран с `next-pwa`. Эвристический Quality Gate и guidance не требуют сети вообще — должны продолжать работать без интернета, синхронизируя находки, когда связь появится.
5. **Готовый биллинг.** Переиспользуется существующая система баланса Doctor Opus, если Sono продаётся как платное дополнение.

## 4. Технический стек (рекомендация для MVP)

- **Next.js 14 + TypeScript** — то же семейство, что и Doctor Opus, для единообразия и переиспользования утилит.
- Веб-платформа, не нативное мобильное приложение — иначе теряется главное УТП «воткнул USB/HDMI-граббер — открыл браузер — заработало».

**Платформенная матрица (проверено по состоянию на 2026):**

| Платформа | HDMI/UVC-граббер через `getUserMedia` | Screen-capture (`getDisplayMedia`) |
|---|---|---|
| Windows/macOS (десктоп-браузер) | Работает | Работает (с повторным разрешением на сессию) |
| iPad (USB-C, iPadOS 17+) | Вероятно работает — Safari использует AVFoundation, где начиная с iPadOS 17 есть нативная поддержка внешних UVC-камер; требует физической проверки | Не работает для стороннего приложения |
| Android (мобильный Chrome) | **Не работает надёжно** — системное ограничение | Не работает для стороннего приложения |

- **Для устройств без собственного видеовыхода** (большинство современных Wi-Fi/USB-зондов) — универсальный путь: **вывод экрана телефона/планшета наружу через USB-C-to-HDMI (DisplayPort Alt Mode)**, а не встроенный `getDisplayMedia`. Внешний граббер ловит это HDMI-зеркало так же, как и видеовыход классического аппарата — метод не зависит от бренда зонда/приложения. Android при этом используется как **источник** сигнала (через зеркало на другое устройство), не как **приёмник**.
- **Явное ограничение MVP**: Android как веб-клиент для HDMI/UVC-пути не поддерживается — либо нативное приложение (см. Фазу 6), либо только режим источника.
- Открытые библиотеки: `getUserMedia`/`enumerateDevices` (встроено в браузер), `dicom-parser` (уже есть в Doctor Opus) или self-hosted **Orthanc** для сетевого DICOM-приёма (опционально, вне MVP).

### 4.1 Покрытие handheld-аппаратов в первой версии

Ключевой факт: **у подавляющего большинства современных хендхелдов — и западных, и китайских — нет собственного видеовыхода.** Универсальный путь для всего класса — зеркалирование, а не адаптер под конкретный бренд.

| Аппарат/класс | Есть физический видеовыход? | Реальный путь подключения |
|---|---|---|
| Дешёвые китайские Wi-Fi/USB-зонды | Нет | USB-C-HDMI зеркало → граббер |
| Butterfly iQ / iQ+ / iQ3 | Нет | Зеркало (iPhone 15+ с USB-C проще) |
| GE Vscan Air (SL / Dual Probe) | Нет | Зеркало |
| Philips Lumify | Нет | Зеркало |
| Clarius (все модели) | Нет, но есть **открытый Cast API** (проверено — публичный, бесплатный SDK) | (а) нативный адаптер через Cast API; (б) fallback — зеркало |
| SonoSite PX / Edge II | **Да** — реальный HDMI/VGA на консоли | Прямой граббер |

**Вывод для Фазы 0**: приоритетно реализовать (1) `uvc-hdmi-adapter` под прямой видеовыход и (2) сценарий "USB-C-HDMI зеркало" как единый путь для всего парка app-based хендхелдов.

### 4.2 Покрытие стационарных входов в первой версии

| Класс системы | Видеовыход | DICOM-экспорт | Реальный путь |
|---|---|---|---|
| Современные карт-системы (GE/Philips/Mindray/Siemens и т.п., последние ~15-20 лет) | Да (HDMI/DVI/VGA) | Да (сеть или hot-folder) | Прямой граббер (Live) + DICOM (Study) одновременно |
| Старые системы (композитный/S-Video выход) | Да, но не HDMI | Иногда | Composite-to-USB граббер + DICOM, если есть |

**Вывод**: стационарные покрываются увереннее хендхелдов — Second Opinion Mode реалистичнее опирается на Live+Study одновременно, Guided Mode для хендхелдов в MVP — практически только Live.

### 4.3 Сводная таблица «аппарат → подключение → что получаем → режим Sono»

| Аппарат/класс | Способ подключения | Что получаем | Режим Sono |
|---|---|---|---|
| Дешёвый китайский Wi-Fi/USB-зонд | Зеркало → граббер | Живой поток, без калибровки | **Guided (Live)** |
| Butterfly iQ/iQ+/iQ3 | Зеркало; опц. Butterfly Cloud | Живой поток [+ опц. DICOM] | **Guided (Live)** [+ Study опц.] |

| Стационарные карт-системы | HDMI/VGA + DICOM | Живой поток + калиброванные исследования | **Second Opinion (Live + Study)** |
| Старые стационарные | Composite-to-USB + DICOM | Живой поток низкого качества [+ DICOM] | **Second Opinion (ограниченно)** [+ Study] |

## 5. Контракт диагностического результата (внутренний для Sono) и интеграции с Doctor Opus

**Диагноз формируется и проверяется целиком внутри Sono, до какой-либо связи с Doctor Opus.** Ниже — внутренний контракт результата (аналог `DiagnosticResult`), затем — облегчённая обёртка для передачи уже готового результата в Doctor Opus.

```ts
type EvidenceRef = {
  evidenceId: string
  frameTimeMs?: number
  region?: { x: number; y: number; width: number; height: number }
}

type Observation = {
  id: string
  feature: string
  polarity: 'present' | 'absent' | 'uncertain' | 'not_assessed'
  evidence: EvidenceRef[]
  source: 'operator' | 'model'
  reviewedByOperator: boolean
}

type PreliminaryDiagnosis = {
  id: string
  label: string
  priority: 'consider' | 'important_to_exclude' | 'most_compatible'
  supportingObservationIds: string[]
  contradictingObservationIds: string[]
  missingEvidence: string[]
  limitations: string[]
  status: 'model_proposed' | 'operator_accepted' | 'operator_rejected'
}

interface DiagnosticResult {
  schemaVersion: '1.0'
  studyId: string
  question: string
  bodyRegion?: { name: string; confirmedByOperator: boolean }
  views: Array<{ name: string; evidenceIds: string[]; operatorConfirmed: boolean }>
  observations: Observation[]
  differential: PreliminaryDiagnosis[]
  outcome: 'hypotheses_available' | 'low_confidence_hypothesis' | 'insufficient_evidence' | 'unsupported_mode' | 'error'
  qualityLimitations?: string[]  // конкретные артефакты/причины неполноты, обязательно при low_confidence_hypothesis
  whyCannotAssess?: string[]
  acquisitionRequests: string[]
  modelProvenance?: { provider: string; model: string; promptVersion: string; createdAt: string }
  formulaSource: 'published-literature'
  clinicallyValidated: false
}
```

**Правило арбитра (обязательное, не опциональное)**: `PreliminaryDiagnosis` без хотя бы одного `supportingObservationId`, чья `evidence` реально ссылается на существующий кадр, — отклоняется арбитром до показа врачу. Никаких процентов вероятности вместо `priority`, пока нет отдельной калибровки на целевой задаче.

**Передача в Doctor Opus (опционально, после подтверждения врачом)** — облегчённая обёртка поверх уже существующего `DeviceStudyEnvelope`:

```ts
interface SonoStudyPayload extends DeviceStudyEnvelope {
  modality: 'ultrasound'
  payloadType: 'image'
  measurements: {
    diagnosticResult: DiagnosticResult   // уже прошёл арбитра и подтверждён врачом
    sourceType: 'uvc' | 'hdmi' | 'dicom' | 'screen-capture'
    sourceTrustLevel: 'high' | 'medium' | 'low'
  }
}
```

Doctor Opus получает уже проверенный `diagnosticResult` и сопоставляет его с анамнезом/другими исследованиями пациента — не запускает диагностическое рассуждение заново поверх сырых данных.

### 6.2 Quality Gate (v1 — без ML)

Эвристики на canvas, считаются за миллисекунды:
- `scoreSharpness` — вариация Лапласиана;
- `scoreBrightness` — гистограмма, отсечка пере-/недосвета;
- `scoreStability` — межкадровая разница (детект смаза от резкого движения);
- `scoreCoverage` — доля кадра, занятая непустым УЗИ-сектором.

Итоговый `qualityScore = weighted(sharpness, brightness, stability, coverage)`. Порог автозахвата — 0.75, держится ≥1.5 сек подряд.

**Явное правило**: если `qualityScore` ниже порога — в LLM ничего не уходит, показывается подсказка, а не результат "на глаз".

**Важное ограничение честности (исправление относительно кода Фазы 0)**: `HeuristicQualityScorer` — чисто технический (`TechnicalFrameGate`), он ничего не знает про анатомию. Подсказки на его основе обязаны звучать технически ("нерезко", "слишком темно", "слишком резкое движение"), а НЕ анатомически ("измените угол/глубину", "найдите орган") — вторая формулировка выдаёт эвристику за понимание, которого у неё нет. Анатомический guidance (куда именно двигать датчик относительно органа) допустим только от `OrganModule.guidance` (текстовый протокол по шагам, §6.3) или от подтверждённой врачом области — не от одной лишь резкости/яркости кадра.

**Архитектурное требование, обязательное уже в Фазе 1** (чтобы не переделывать в Фазе 7): `computeQuality()` вызывается через интерфейс-стратегию, а не напрямую:
```ts
interface QualityScorer {
  score(gray: Float32Array, width: number, height: number, prevGray: Float32Array | null): QualityScore
}
// HeuristicQualityScorer (Фаза 0-1) и MLQualityScorer (Фаза 7) реализуют один интерфейс —
// замена в Фазе 7 не требует переписывания вызывающего кода.
```

### 6.3 Organ Module Registry

```ts
interface OrganModule {
  id: string
  title: string
  requiredViews: string[]
  qualityThreshold: number
  isFrameAcceptable(frame: UltrasoundFrame, score: QualityScore): { ok: boolean; reason?: string }
  computeMeasurement(frames: UltrasoundFrame[]): MeasurementResult
  toFindingsPayload(result: MeasurementResult): SonoStudyPayload['measurements']
}
```

**Модуль 1 — Мочевой пузырь (полная реализация в MVP, Фаза 1)**
- Требуемые виды: поперечная + продольная плоскость.
- Формула объёма: `V = Д × Ш × В × 0.52` (эллипсоидная аппроксимация, стандартная в POCUS).
- Guidance: найти пузырь над лобковым симфизом → поперечная плоскость, зафиксировать ширину → повернуть на 90° → продольная плоскость, зафиксировать длину и высоту.
- Findings: `{ volume_ml, view_transverse_quality, view_longitudinal_quality, confidence }`.

**Модуль 2 — IVC (тонкий срез, Фаза 2, НЕ полная реализация)**
- Цель — проверка, что контракт `OrganModule` выдерживает **временной ряд** (диаметр вены на вдохе/выдохе), а не только статичную плоскость.

**Модули 3-5 (Фаза 4, можно параллельно)**: eFAST (бинарный скрининг жидкости на 4 точках), лёгкие (подсчёт B-линий), щитовидная железа (та же эллипсоидная формула, что и мочевой пузырь).

**Модуль 6 — Кардио/EF (Фаза 5, после Фазы 2)**: см. §9.

### 6.4 LLM Pipeline: Brain 1 → Brain 2 → Диагностический арбитр (всё внутри Sono)

**Brain 1 — Gemini 3.8** (`lib/llm-pipeline/sono-brain1.ts`): получает один отфильтрованный лучший клип + уже посчитанное `computeMeasurement()`-число. Возвращает **не свободный текст**, а список `Observation[]` — каждое наблюдение обязано нести `evidence: EvidenceRef[]`, указывающий на конкретный кадр/область. Наблюдение без ссылки на реальный кадр не может попасть дальше по конвейеру — это проверяется на уровне парсинга ответа, до Brain 2.

**Brain 2 — Claude Sonnet / GPT-5.6** (`lib/llm-pipeline/sono-brain2.ts`): **новый компонент, не переиспользование `getDirectivePrompt` из Doctor Opus.** Системный промпт — роль опытного врача УЗИ-диагностики (не общий клинический промпт Doctor Opus). Вход — `Observation[]` от Brain 1 + клинический вопрос врача (если задан) + `bodyRegion` (если подтверждён). Выход — `PreliminaryDiagnosis[]` со связкой `supportingObservationIds`/`contradictingObservationIds`, без итогового вердикта — только ранжированный дифференциал с явными "за"/"против".

**Диагностический арбитр** (`lib/diagnostic-arbiter/arbiter.ts`) — не LLM-вызов, а детерминированная валидация на выходе Brain 2:
- отклоняет `PreliminaryDiagnosis` без хотя бы одного реально существующего `supportingObservationId`;
- отклоняет числовые проценты вероятности вместо `priority`-меток;
- при внутреннем противоречии (например, "important_to_exclude" без единого поддерживающего наблюдения) — понижает `outcome` результата до `insufficient_evidence`, добавляя причину в `whyCannotAssess`;
- проверяет соответствие заявленной `bodyRegion`/`view` тому, что реально подтвердил врач, не давая модели "тихо" расширить область исследования за пределы того, что было отснято.

**Режим низкого качества/артефактов — не отказ, а явно помеченная гипотеза (важно для Guided Mode, "для чайника").** Если изображение содержит артефакты, часть протокола не выполнена или качество ниже идеального, но **какие-то** наблюдения всё же получены (пусть и с `polarity: 'uncertain'`) — Brain 2 не обязан молчать. Он может строить гипотезы поверх неопределённых наблюдений, а Арбитр пропускает такой результат с `outcome: 'low_confidence_hypothesis'` и обязательным заполнением `qualityLimitations` (конкретно — какой артефакт, какая часть протокола не выполнена). Это соответствует тому, как реально работает УЗИ-диагност: не "исследование невозможно интерпретировать", а "ограничено артефактом X, находки требуют технически более качественного повтора".

**Граница, которую нельзя пересекать даже в этом режиме**: Brain 2 может **рассуждать** поверх неполных/неопределённых данных (это нормальное дифференциальное мышление), но не может **сочинять** данные, которых не извлёк Brain 1 — то есть заявлять конкретное измерение или наблюдение, не имеющее реальной `evidence`-привязки. Арбитр проверяет это одинаково строго в обоих режимах: разница между `hypotheses_available` и `low_confidence_hypothesis` — в качестве и полноте исходных наблюдений, не в строгости проверки происхождения гипотезы.

**Doctor Opus — опционален, подключается после подтверждения врачом.** Получает уже прошедший арбитра и просмотренный врачом `DiagnosticResult` (см. §5) и сопоставляет его с анамнезом/другими исследованиями пациента — не переигрывает диагностическое рассуждение с нуля. Без подключения к Doctor Opus вся диагностическая функция Sono работает самостоятельно (это принципиальное отличие от предыдущей версии ТЗ, где Doctor Opus был обязательным звеном).

## 7. Нефункциональные требования

- **Латентность Guided Mode**: обратная связь по наведению — не реже 10 Гц, полностью локально, без сетевого вызова.
- **Приватность**: любой кадр, уходящий в LLM, проходит тот же пайплайн анонимизации, что уже есть в `lib/video-frame-extractor.ts` Doctor Opus (переиспользовать, не писать заново).
- **Прозрачность источника**: каждый результат хранит `sourceTrustLevel` — `screen-capture` всегда ниже, чем `uvc-hdmi`/`dicom`.
- **Право сказать «недостаточно данных»**: если `qualityScore` не достигнут — явный отказ, а не результат с низкой уверенностью, выданный как найденный.
- **Дисклеймер**: Sono — вспомогательный инструмент, черновик, требующий подтверждения врача.

### 7.1 Регистр рисков (обязателен — Sono теперь сам формулирует диагностические гипотезы)

| Риск | Контроль |
|---|---|
| Ложное успокоение при пропуске находки | `outcome: insufficient_evidence` вместо тихого "патологии не обнаружено", если не все требуемые виды получены |
| Сочинённое наблюдение под видом гипотезы "низкой уверенности" (Guided Mode) | `low_confidence_hypothesis` разрешает рассуждение над `polarity: 'uncertain'`, но не отменяет требование реальной `evidence`-привязки — арбитр проверяет это одинаково строго в обоих режимах (§6.4) |
| Убедительная, но необоснованная гипотеза модели | Арбитр отклоняет `PreliminaryDiagnosis` без реальной `evidence`-привязки (§5-6.4) |
| Числа/проценты, создающие ложное ощущение точности | `priority` — не число; проценты вероятности запрещены до отдельной калибровки |
| Перепутанная сторона/локализация | `bodyRegion.confirmedByOperator` обязателен перед показом дифференциала как значимого |
| Измерение без подтверждённого масштаба, выданное как число в мм/мл | `calibration: 'unavailable'` → `value: undefined`, не приблизительное число (уже в §5-6.3) |
| PHI, впаянное в пиксели кадра (не только в метаданных) | Анонимизация кадра (переиспользуется из `lib/video-frame-extractor.ts`, §3.1) применяется до, а не после отправки в LLM |
| Подмена вывода модели после ручной проверки врача | `status: 'operator_accepted' / 'operator_rejected'` фиксируется неизменяемо в `DiagnosticResult`, не перезаписывается повторным вызовом модели |

## 8. Общие правила для агента (Cursor / Grok 4.7 / GPT-5.3-Codex) на всех фазах

1. **Одна фаза — один прогон.** Не начинать следующую фазу, пока предыдущая не прошла критерий приёмки.
2. **Тесты пишутся вместе с кодом, не после.** После каждого модуля — `npx vitest run`, вывод приложить к отчёту.
3. **Не трогать клиническую достоверность.** Каждый результат измерения обязан нести `formulaSource: 'published-literature'` и `clinicallyValidated: false` — это постоянное поле контракта, не временная заглушка.
4. **Не реализовывать пункты из §11** без явного перехода по условиям §11.1 — если задача решается легче через один из этих пунктов, значит задача сформулирована неверно.
5. **Коммитить малыми проверяемыми шагами**, не одним гигантским коммитом на всю фазу.
6. **Формат отчёта в конце фазы** — см. §13.

### Фаза 2 — Модуль IVC (тонкий срез, проверка контракта на временном ряде)

**Цель**: проверить, выдерживает ли `OrganModule` данные другой формы (серия кадров с изменяющимся диаметром), не только статику.

`lib/ultrasound-modules/ivc/measurement.ts`:
```ts
// Индекс коллапсибельности = (Dmax − Dmin) / Dmax по серии кадров одного дыхательного цикла
export function computeCollapsibilityIndex(diametersMm: number[]): number {
  const dMax = Math.max(...diametersMm)
  const dMin = Math.min(...diametersMm)
  return (dMax - dMin) / dMax
}
```
Диаметр в MVP — не автоматическая сегментация (ML, вне рамок), а ручной ввод врачом опорных точек либо простая эвристика по перепаду яркости вдоль линии.

`lib/ultrasound-modules/ivc/ivc.test.ts` — синтетическая серия значений → ожидаемый индекс.

**Критерий приёмки**: если `OrganModule`/`UltrasoundFrame` пришлось менять — явно описать что и почему (ожидаемый полезный результат фазы, не ошибка); если не потребовалось — тоже зафиксировать явно.

### Фаза 7 — Обученные ML-модели (заменяют эвристики Quality Gate)

**Зависимость**: собственный поток размеченных данных из реальной эксплуатации Фазы 1. **Не начинать без данных.**

## 10. Вместо фазы «Реверс-инжиниринг» — план официального доступа к вендорским API

Не фаза кода — работа для команды, но результат разблокирует адаптеры Яруса 2 из §4.1.

1. Список приоритетных вендоров — по факту наличия у пользователей (§4.3), не по величине бренда.
2. Найти канал: публичный developer-портал (как у Clarius) или partnership/developer relations контакт на сайте вендора — не техподдержка.
3. Формулировка запроса: не "дайте доступ к внутреннему протоколу", а "мы разрабатываем вендор-нейтральный клинический ассистент, увеличивающий клиническое использование вашего устройства через уже открытые каналы (HDMI/DICOM); хотели бы обсудить официальный developer API".
4. Пока ответа нет/отрицательный — устройство работает через Ярус 1 (HDMI/UVC или зеркало) — отсутствие вендорского API не блокирует покрытие, только снижает точность/удобство.

## 12. Открытые вопросы — решены

1. **Платформа MVP**: Windows/macOS-десктоп основная; iPad (USB-C) вероятный второй вариант; Android — только как источник сигнала, не приёмник (§4).
2. **Вендор для тестирования**: не привязываемся к конкретному — тестируем универсальный путь "USB-C-HDMI зеркало → граббер → браузер" (§4.1).
3. **Валидация формулы vs клиническая валидация — не одно и то же:**
   - *Корректность реализации* — юнит-тесты на синтетических данных с известными размерами, доступно без пациентов (см. Фазу 0, 17/17 тестов).
   - *Клиническая валидация* — отдельный поздний этап (проспективное исследование), обязателен перед показом результата как «готового», не блокирует написание/тестирование кода.
   - Практическое следствие: каждый результат несёт `formulaSource: 'published-literature'`, `clinicallyValidated: false`.
